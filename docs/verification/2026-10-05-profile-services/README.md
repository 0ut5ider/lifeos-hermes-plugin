# Profile service drain and recovery

Date: 2026-10-05. The tests use the actual Fedora user systemd manager and 33 isolated service units. Each unit runs a real Python parent and child writer. The tests create runtime links to private fixture definitions, then remove those links and stop the units during cleanup. No production service changes.

`ProfileServices` binds the gateway, dashboard, and native PULSE roles to fixed server-owned unit names. The default bindings are `hermes-gateway.service`, `hermes-dashboard.service`, and `com.lifeos.pulse.service`. Each service must use the selected profile, account home, or installed native PULSE working directory. The source fingerprint covers the effective static service properties and the physical unit and drop-in file digests. The journal stores the fingerprint instead of launch arguments or file contents. Escaped drop-in path formats require review.

The private journal records all original active states and stop intent before the first stop. The stop order is gateway, native PULSE, then dashboard. This keeps the authenticated endpoint available while the gateway and native PULSE drain. The barrier checks that each main process stops and that both the observed and original control groups contain no parent or child writers. It checks the caller's own user-manager control group namespace. A writer that restarts after the drain invalidates `verify_stopped`.

Restart follows dashboard, native PULSE, then gateway. Recovery restarts only services that were active at admission. It retains an originally inactive service. A changed unit definition refuses before restart. A definition change during drain leaves the remaining services running and preserves recovery state. Recovery can continue after process exit during either stopping or starting. It reuses an already started dashboard instead of restarting it again.

The initial three feature controls fail because the module does not exist. The first implementation refuses Fedora's default service drop-in. Instrumentation also shows that the printable `ExecStart` value contains changing process metadata. An attempted separate D-Bus lookup fails after systemd unloads a stopped unit. The accepted implementation fingerprints the unit and drop-in definitions and uses the one `systemctl show` response for live process state. These failed approaches and actual observations remain in this directory.

The native systemd property uses `!` to encode an optional working directory. The check resolves that form before comparing the selected physical directory. This behavior is verified against the [systemd 259 property implementation](https://github.com/systemd/systemd/blob/v259/src/core/dbus-execute.c). Control group emptiness uses the kernel's `populated` field, which includes descendants. See the [kernel control group version 2 documentation](https://docs.kernel.org/admin-guide/cgroup-v2.html).

A read-only `.212` check confirms that `.claude` resolves to `.hermes`. The service transaction captures both the declared installed root and its physical root. A stable alias can select the same physical services. Retargeting the alias refuses recovery before any restart. The alias controls first fail because the initial implementation requires a direct working-directory path. Their failing output remains in `alias-before-output.txt`.

The final gate passes **28 tests and 29 subtests in 38.98 seconds**, with no skips, failures, or errors. It includes 11 actual service controls, 14 ownership configuration controls, and three installation lock controls. Ten service outcomes and 14 ownership outcomes are retained. Invalid service values have six subtests. The native manager and child writer results are actual process effects, with no service mocks.

`final-command.json` records the command, environment, and source hashes. `final-output.txt` and `final.done` retain the passing result and exit status. `source-comparison.json` confirms unchanged sources at the end of the gate. `cleanup-observation.json` confirms that no fixture unit remains. The first filtered no-match cleanup query returns exit status 1 with no output. The corrected full listing returns 0 and contains no selected fixture names. No existing unit file is edited. This unit adds no dependency or upstream patch.

## Remaining ownership requirements

This internal barrier does not publish ownership configuration, create backups, restore programs, verify application endpoints, or verify an owner model turn. Every receipt reports `owner_turn_verified: false`. The combined coordinator must verify the stopped barrier immediately before its protected work and handle detached jobs and other supported writers. The installation lock serializes each barrier call; it does not yet hold one lease across the entire backup and ownership sequence.

The test services exercise actual process behavior through synthetic writers. They do not run the native gateway, dashboard, or PULSE applications as services. Those applications and their selected source versions still need the combined acceptance installation. No dashboard or Hermes ownership activation action is added. Production ownership, import, background jobs, private-model acceptance, voice, and release verification remain open.

# Off-server container recovery

Date: 2026-10-08. This check uses the authorized disposable installation container on Proxmox `.101`. It does not change VM `801` or the source container.

The configured `PBS-01` storage points to Proxmox Backup Server at `192.168.8.24`, datastore `PlutoNAS_Backup`. The [backup log](ct100-backup.txt) records a successful snapshot backup of container `100` to `ct/100/2026-10-08T16:10:54Z`. The [restore log](ct102-restore.txt) records a successful restore to new container `102`. Both completion markers contain zero.

The restored container receives a unique network address. The operator disables its network link and automatic boot before starting it. The restored account cannot contact model services or Discord. The container hostname is `lifeos-recovery-probe`. This container is a recovery fixture, not the daily server.

The [comparison](file-comparison.json) verifies seven selected file hashes across the original and restored installation. These files include Hermes configuration, identity, native memory configuration, plugin source, Hermes source, and both native hot memory files. The restored SQLite history contains the same eight sessions and 22 messages. The database comparison uses row counts and does not export message content. The restored guest boots successfully with its network link down.

The backup destination is another server address. This check does not establish independent physical hardware or storage failure domains. It also does not verify the final daily candidate. A separate development-profile snapshot and recovery check retains coherent application backup evidence.

The Proxmox job `lifeos-dev-offserver` now schedules development container `101` every day at `03:00` in the host timezone, `America/Atikokan`. The [schedule receipt](backup-schedule-receipt.json) verifies its enabled state, selected container, storage, snapshot mode, and next run. Its first scheduled run is `2026-10-09T04:00:00-04:00` in Toronto, or `08:00` UTC. The job uses the existing storage retention policy. It does not prune unrelated backup groups. The [manual development backup](ct101-backup.txt) uses the same storage and snapshot mode and completes successfully in 12 minutes 24 seconds. Its archive is `ct/101/2026-10-08T16:23:42Z`.

These container snapshots preserve a filesystem crash state, including committed SQLite journals and native recovery journals. They include the separately verified coherent profile snapshot. They do not drain application services on each scheduled run. The final daily guest needs its own scheduled job and acceptance receipt after provisioning.

To undo this external schedule, disable or remove only `lifeos-dev-offserver` through the Proxmox backup job API. No pre-existing backup schedule changes. Container `102` restores with automatic boot disabled and its network link down. After the recovery comparisons pass, the operator stops and removes this disposable fixture. The source container and PBS archive remain intact.

The [development restore](ct103-restore.txt) reconstructs container `101` as new disposable container `103`. It processes 85.255 GiB in 18 minutes 35 seconds and exits successfully. The operator disables the restored network link before boot. Container `103` has automatic boot disabled, two CPU cores, and a 4 GiB memory limit. Its gateway starts while isolated and then the operator stops and disables that fixture gateway. The live `.252` gateway stays active. The restored guest receives no LAN address and is not the daily server.

This checks the deployed development code, not the staged daily candidate.

## Conclusion

No. The inspected public extension contracts do not provide all control points that full LifeOS hook parity requires. A plugin can own LifeOS policy, payload translation, subprocesses, remote project trust, transcripts, tier mapping, and carrier probes. Hermes must own authoritative prompt rejection, universal stop continuation, approval floor ordering, authoritative tool identity, and final model context delivery. Moving these into Python monkeypatches or copied built-in tools changes where the fork lives, not whether there is a fork.

The smallest maintainable design is a plugin plus a small generic Hermes extension contract and upstream LifeOS correctness fixes or generic carrier adapters. Some individual patches can disappear, but no evidence supports deleting all 16 today. The current patched integration also has documented parity gaps; these patches are not proof of full parity.

### Hook-control patch breakdown

1. Prompt block: add a typed host decision before provider execution and durable user-turn persistence. An exception from middleware is not a safe replacement: middleware's own error before next_call is caught and execution continues. A fabricated provider response may avoid a request but does not implement rejection/history semantics.
2. Stop: add a universal candidate-answer gate independent of changed files, with effective model/effort, attempt, session, and turn identity. Define the continuation cap explicitly. The present default eight-block cap eventually permits termination; do not call that an unlimited mandatory gate.
3. Tool context: add append-after-transform context with original result and normalized error status. Ordinary post_tool_call is an observer. Tool execution middleware wraps execution but cannot guarantee later transforms retain its output.
4. Approval: add a narrowly scoped responder after hardline and user-deny floors. Preserve Tirith findings and smart guardian denial. A LifeOS allow may resolve a recoverable warning, never suppress these higher-authority checks.
5. Updated input plus approval: host should bind approval to the transformed arguments. Splitting modification into request middleware is potentially possible, but must run LifeOS once and preserve arguments, call identity, ordering, and the exact approved input. It is not a reason to remove the behavior without regression tests.
6. Terminal failure: add a terminal turn outcome event. api_request_error alone includes transient errors that later recover. StopFailure needs the final turn result, not every provider exception.
7. Inner code-execution calls: carry session/turn authority through each local and remote RPC cell. Session identity must come from the host dispatch context, not model arguments or a process-global plugin variable.

Current Hermes supports four middleware kinds, tool_request, tool_execution, llm_request, and llm_execution. It also supports opt-in built-in tool replacement through register_tool(..., override=True). These are useful APIs, but none supplies a complete turn-admission and finalization contract. Unknown hook names being accepted into a registry does not mean a host call site ever fires them.

## Concrete safety defect found

lifeos_hook_bridge/bridge.py:1199, HookBridge.command_approval, loops through native PermissionRequest outcomes and returns on the first allow. It does not aggregate native deny outcomes or an exit-code-2 block. Therefore a later native deny can be discarded. The Hermes patch only combines results across Hermes plugin callbacks, so its deny-wins behavior does not fix aggregation inside this one callback.

Fix: execute the configured native outcomes, validate that event-specific decisions belong to PermissionRequest, collect allows and denials, and return deny if any applicable native denial/block occurs. Return allow only if at least one applicable allow and no denial exists. Test both allow/deny orderings, exit-code-2 denial, neutral outcomes, and wrong-event outputs. Then run the real Hermes command guard tests to show a bridge allow still cannot override hardline, user-deny, Tirith, or guardian denial. Parent reviewer independently confirmed this defect and intends to fix it.

## Minimal design and verification order

1. Define a parity ledger by registration and observable effect, including event payload, timing, veto, context, transcript, side effects, and lifecycle. The 74 registered hooks are the target. Tests passing for dispatch alone do not prove their effects.
2. Preserve the existing Hermes safety floors and fix native deny aggregation first. Prove the negative paths through real host guard entry points.
3. Upstream generic Hermes prompt/stop/outcome/approval/context contracts, nested dispatch authority, backend stale-write guard, and runtime launcher correction. Combine related files into coherent upstream changes; patch file count is not architectural quality.
4. Extend existing public subagent and LLM services with provider/model/effort, explicit fallback policy, and effective route evidence. Keep credentials owned by Hermes. Keep LifeOS tier naming and carrier evidence in the plugin.
5. Upstream LifeOS's checkpoint, transcript parser, desktop gate, and filename/normalization correctness fixes. Introduce small generic adapters for session counting, backend observations, and carrier checks. Avoid Hermes-specific executable paths in shared native logic.
6. Only then remove corresponding local patches, rerunning clean-source install, native hook effects, host denial regression, provider isolation, and remote concurrency scenarios. Removing a patch requires evidence against unpatched dependencies or accepted upstream changes.

Remaining full-parity limits include private transcript differences, unsupported remote backends, file-based polling instead of all native managed config sources, arbitrary Python subprocess/file effects in execute_code outside inner tool dispatch, merged terminal streams, and external-service-dependent native effects. The report in docs/hook-parity.md explicitly says full parity is not achieved. Preserving all current tested behavior is a narrower claim than completing full parity.

Review emphasis: approval authority and prompt admission are the highest safety boundaries. Carrier evidence must identify the route that actually executed. Remote file tests must distinguish target identity and full observed content, and should not claim an atomic compare-and-write guarantee from a pre-write digest check alone. The proposed plugin-only substitutions are design options, not tested implementations.

# LifeOS hook parity record

This record describes the public LifeOS hook settings installed from commit `5e2f2e8` on 2026-09-27. It distinguishes registered callbacks from verified behavior. The bridge is a Hermes plugin. It does not edit LifeOS source files.

## Event coverage

| Claude Code event | Registrations | Hermes path | Current result |
| --- | ---: | --- | --- |
| `PreToolUse` | 6 | `pre_tool_call` | Command and local HTTP hooks execute for mapped and unmapped Hermes tools. Exit code 2 and deny decisions block. Updated input maps back to Hermes arguments. An outer `execute_code` also presents its Python source as a Bash command to named Bash guard groups. |
| `PostToolUse` | 32 | `augment_tool_result` | Hooks execute after the existing result transform. Their `additionalContext` and exit-2 stderr are appended to the model-bound result. Plain exit-0 stdout stays out of model context. Content-bearing Hermes browser results also reach `WebFetch` matchers while generic hooks keep the Hermes tool name. |
| `UserPromptSubmit` | 9 | `pre_llm_call` | Hooks execute before the current prompt enters the bridge transcript. A block prevents model processing and discards the current prompt from bridge and Hermes history. For multimodal content, the hook receives the text portions joined with newlines. Allowed hook context is added to the current user turn. Async hooks start without blocking. |
| `Stop` | 8 | `pre_turn_stop` | Hooks execute on each text answer. A block withholds the candidate from Hermes user delivery and session history, then continues the same turn up to eight times by default. At the continuation limit, the default allows the answer as Claude Code does; the plugin's `fail_closed` setting instead returns an incomplete result. Iteration-budget exhaustion also returns an incomplete result. `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP` overrides the continuation limit. The native hook sees the prior transcript and the current answer in `last_assistant_message`; the bridge appends the current answer after the hook. A private transcript supplies `transcript_path`. |
| `SessionStart` | 5 | first `pre_llm_call` | Hooks execute before the first user prompt is sent to the model. Their text output joins that prompt's context. Hermes's first-turn flag supplies `source: startup` or `source: resume`; a persisted transcript supplies the fallback when that flag is absent. |
| `SessionEnd` | 6 | `on_session_finalize` | Handlers run concurrently, matching Claude Code's hook contract. All six installed handlers completed successfully on a synthetic session boundary. A real one-shot Hermes CLI shutdown also reached a temporary native SessionEnd hook. Native SessionCleanup removed a synthetic session-name entry, IntegrityCheck recorded a synthetic hook edit, WorkCompletionLearning created a learning, MemoryHealthGate wrote a health row, and DocIntegrity emitted a memory inventory finding. | `PermissionRequest` | 2 | `pre_command_approval` for Bash and `pre_tool_call` for files and MCP | Native `Safety.hook.ts` runs for guarded Bash commands that may need permission; simple probed `pwd` and unquoted `echo` forms skip this event unless a matching or unsupported deny or ask rule requires review. The native bridge executes the installed registration types with partial coverage of `ConfigChange` and Bash `PermissionRequest`. Literal local Bash rules are tested against Claude Code 2.1.272; parser-backed compound Bash rules, wildcard allows, and documented wrappers are supported for tested forms. Redirects to `/dev/null` or file descriptors and here-docs have no file target and can use a matching Bash allow. Literal redirect and `tee` file targets check `Read` and `Edit` deny and ask rules before a native Bash hook grant. Literal file operands of `cat`, `head`, `tail`, `sed`, `wc`, `grep`, `rg`, `cut`, `awk`, `stat`, `diff`, `sort`, `ls`, `file`, and `find` are checked, including forms reached through recognized Bash wrappers. `sort -o` also checks its output against Edit rules. A literal `cd` changes the directory used for following file targets; uncertain directory changes request review. `sed` scripts stay on the review path because they can open additional files. The bridge uses settings-source anchors and gitignore-style path patterns for those targets. Dynamic targets, other file-opening Bash commands, uncommon shell forms, and non-file managed sources remain incomplete. Remote file-rule checks now resolve paths in the owning backend. If that probe fails, Bash and direct file tools request human review. SSH and Docker symlink denials passed live isolated tests; other remote backends and path forms remain unverified. See [the redirect file-rule probe](../notes/2026-09-28-redirect-file-permission-gap.md), [the reader operand probe](../notes/2026-09-28-reader-file-permission-gap.md), [the named file command probe](../notes/2026-09-28-named-bash-file-commands.md), [the search and awk probe](../notes/2026-09-28-search-and-awk-file-rules.md), [the directory-change probe](../notes/2026-09-28-compound-cd-file-rules.md), and [the remote symlink probe](../notes/2026-09-28-remote-symlink-file-rules.md). Trusted SSH and Docker project Bash deny rules passed live isolated workspace tests. The Docker probe also verified a compound deny and a remote skill-file digest. The bridge reads local managed JSON files before each Bash decision, including drop-ins; a matching deny blocks despite a user allow. The file-based `allowManagedPermissionRulesOnly` lock excludes user and project Bash rules when enabled. Hermes safety denials still apply after this bridge decision. See [the permission rule probe](../notes/2026-09-28-bash-permission-rules.md). The MCP `PermissionRequest` registration executes, but Hermes's trusted-server policy can still differ from Claude Code's permission rules. Direct Read, Write, and Edit calls now apply literal `Read` and `Edit` deny rules before a native hook grant. Matching ask rules request human review even after a hook grant. A multi-file patch checks every target, while Hermes file guards and approval scope can still differ from Claude Code. For new Hermes todo IDs and kanban task calls, the patched native `TaskCreated` hook now runs with session-owned counts. The bridge retains a policy fallback for unpatched LifeOS installs. This is an event-level mapping, not a count of passing behavioral tests. Hermes tool names currently mapped are `terminal`, `read_file`, `write_file`, `patch`, `clarify`, `delegate_task`, `web_search`, `web_fetch`, `web_extract`, `skill_view`, and `tool_search`. The bridge keeps every other Hermes tool name, including `mcp__*`, so generic hooks and the transcript see it. `web_extract` maps to `WebFetch` so the native Safety hook can inspect fetched page content. Content-bearing browser tools reach `WebFetch` PostToolUse matchers without changing their name for generic hooks or the transcript. An outer `execute_code` script reaches named Bash PreToolUse groups with its Python source as `command`; generic hooks still see `execute_code`. Bash command rewrites do not change Python source. Hermes `clarify` maps to Claude Code `AskUserQuestion` for the installed tab-state hooks. Claude Code `MultiEdit` has no exact Hermes tool mapping. Batched Hermes delegation now runs the `Agent` hooks per child with a description, prompt context, background state, and explicit model when supplied; Hermes has no matching Claude subagent type, so the bridge labels each child `general-purpose`. Local Pulse routes fail open when Pulse is not running, as they do in Claude Code. Project hook registrations load only from roots in Hermes's `skills.trusted_project_dirs`. User, project, and local hook groups run in that order for the matching project session.

# Updating the Hermes and LifeOS bridge

The current bridge is a tested combination of three independent code bases. The plugin does not yet update Hermes or LifeOS. Its source preparation command builds the pinned combination from known base commits; it is not an updater for a later release.

| Component | Current test source | Update risk |
| --- | --- | --- |
| Hermes | Base `758ad514eb0e800547e015edf05aa18f78b78d82` plus eleven patches | Stock plugin events do not provide every LifeOS control. A normal source update can switch away from the patched feature branch or leave untested patch merges. |
| LifeOS | Base `5e2f2e8c0abde612da0e99c16c0d07d4ec21b88c` plus nine patches | Hook files and registrations can change. The current `DeployCore.ts` uses `copyMissing`, which does not replace an already installed system file. Repeating the install commands alone cannot prove deployed hooks match a new source release. |
| Bridge plugin | Public Git commit pinned during install | A plugin update cannot restore missing Hermes events or port LifeOS source changes. Hermes refuses automatic updates of a pinned plugin. |

## Rule for the current `.212` test installation

Do not use the Hermes dashboard Update button or `hermes update` to advance this patched test install. Do not run a LifeOS update over its deployed hook tree. The test account now sets `updates.auto_switch_parked_branch: false` in `~/.hermes/config.yaml`. Hermes documents that this prevents a clean parked feature branch from being switched to the update target. This guards one failure mode only. The setting can be reverted with `hermes config set --force updates.auto_switch_parked_branch true`; the prior config is backed up at `~/.hermes/config.yaml.before-update-guard-20260928`.

## Required update workflow

1. Choose exact upstream Hermes and LifeOS commits and one exact bridge plugin commit. Record the three revisions as a tested compatibility set.
2. Prepare new source trees away from the running install. Port each required change to those revisions. Stop if any patch conflicts or if an upstream change makes a patch unnecessary.
3. Compare the new LifeOS hook registration manifest and deployed system files. Check every registration against the bridge event map. Do not advance the LifeOS version marker while files remain stale.
4. Run the bridge suite, Hermes core tests, native LifeOS hook tests, and live `.212` checks for the affected events, including the local model routes and Discord watchdog path when those parts change.
5. Back up the running code, Hermes profile, and LifeOS data separately. Keep user-owned `USER/` and `LIFEOS/MEMORY/` content out of system-file replacement. Hermes's quick update snapshot covers selected state files, not application code.
6. Install the tested source and plugin revisions, restart the gateway, and verify the running code, hook registrations, and model route. If a gate fails, restore the code and data snapshots before accepting another message.

The staged update and rollback automation in steps 2 through 6 does not exist yet. The current preparation command covers only the pinned source pair in step 2. A future LifeOS Bridge **Check for updates** control should show compatible versions and test results. **Apply update** should be available only for a tested compatibility set with a recoverable snapshot. The button must not blindly call `hermes update` or repeat `DeployCore.ts --apply`.

The long-term way to reduce this maintenance cost is to contribute the generic Hermes hook events upstream and make the LifeOS handlers accept Hermes event data upstream. Until both sides contain those changes, the compatibility set and staged verification remain necessary.

**Why existing extension APIs do not immediately replace the patches**

Hermes already supplies registration for tools, lifecycle callbacks, middleware, memory providers and commands. The integration uses those APIs in lifeos_hook_bridge/__init__.py and memory_provider.py. It is not ignoring the native plugin model. The relevant question is whether an extension runs before the protected effect, propagates refusal, and carries current identity. The ordinary observer contract does not supply those properties everywhere.

The current public [middleware contract](https://hermes-agent.nousresearch.com/docs/developer-guide/middleware) documents request rewrites and execution wrappers. Its existence supports implementing integration policy in a plugin. It does not prove fail-closed admission. At current Hermes f925b01791fe052e7d55dc975750c0bd985aff91, [middleware.py lines 198-214](https://github.com/NousResearch/hermes-agent/blob/f925b01791fe052e7d55dc975750c0bd985aff91/hermes_cli/middleware.py#L198) catches a callback exception and calls the next stage if the callback has not done so. That is why removing required middleware would change privacy and failure behavior. Returning a fabricated provider response, raising BaseException, or replacing methods at import time is not a supported equivalent.

The current [plugin registration source](https://github.com/NousResearch/hermes-agent/blob/f925b01791fe052e7d55dc975750c0bd985aff91/hermes_cli/plugins.py#L937) still registers middleware without the required flag. Its hook catalog lacks this integration's pre_prompt_admission, pre_message_delivery, pre_turn_stop and on_turn_result contracts. Native pre_verify is tied to verification behavior and its own budget. It cannot simply replace a stop gate that must run on a no-code conversational turn and withhold an answer at the configured limit. Session-finalization observers remain useful, but adding a callback does not repair missing invocation, cancellation or delivery identity at a native call site.

A pre_tool_call plugin can rewrite or deny a model-visible tool. It cannot by itself preserve command checks made inside execute_code RPC, batch review consumption, remote kernels, or a lower-level protected write. Reimplementing those tools under an override would move the same maintained fork into the plugin, with additional schema and lifecycle responsibilities. That may lower the patch-file count while increasing divergence.

A global delegation model setting does not implement per-task Haiku/Sonnet/Opus/Fable model and reasoning effort selection within one batch. Current [delegate source](https://github.com/NousResearch/hermes-agent/blob/f925b01791fe052e7d55dc975750c0bd985aff91/tools/delegate_tool.py#L645) still describes inherited or configuration-pinned children. A custom model provider could become a real routing boundary, but an equivalent replacement must carry per-child route identity and effort, prevalidate every task, and preserve credentials and failure semantics. This is an architectural proposal with no measured patch reduction. Renaming every tier to the same private model string loses the low/medium/xhigh distinction.

Selecting the native Hermes memory provider does not make built-in memory administration disappear. The plugin-events patch also makes disabled built-in sources stay disabled in learning graph/mutation paths and on malformed configuration reads. A configuration-only replacement must prove those non-provider callers fail closed, including failure to read configuration. Current upstream memory_tool still describes malformed sections as default-enabled.

The LifeOS side already routes many operations through the new MemoryAccess module and reuses native rendering rather than duplicating whole tools. Examples include supplied-source RenderSoul, native Knowledge enumeration, native personal-view renderers, proposal transactions and structured prepare/check/publish jobs. The large memory patch changes 108 paths because native readers and writers do not all pass through MemoryWriter or Pulse's data plane. The independent CLI, hooks, collectors, background jobs and HTTP handlers still need their own entry admission or safe pure exports. A single MemoryWriter replacement or an MCP server covers its callers; it does not govern direct filesystem readers, legacy writers or a detached publisher.

For a concrete chokepoint proposal, centralize managed HTTP request dispatch before Pulse routes enter module handlers. Start with the personal-view family: Books, Projects, Assets, Evals, Threatmodel, Ledger and Doctor. The current MemoryAccess.memoryHTTPPersonalView already centralizes that family's policy. Moving its invocation into one dispatcher could remove repetitive module admission lines, but their supplied-source render exports and job/health behavior still remain. Do not claim seven fewer modified modules. Direct imports, standalone handlers, polling/SSE, health aggregation and async job routes must be inventoried before removing any local admission. The remaining exports explain why centralization may reduce hunks modestly without reducing modified paths. This proposal was inspected, not implemented or proven equivalent.

A more substantial long-term reduction needs upstream-supported source providers and publication boundaries. Admit immutable source snapshots, invoke native pure functions, then revalidate authority and publish through owner transactions. Submit these seams as general APIs. They can remove local divergence if accepted upstream. Runtime filesystem interception, Bun preload hooks, import rewriting, aliases to different implementations, FUSE-like projections or monkey-patched module functions are not counted as reductions here. A sandboxed stock-native snapshot worker is a possible separate architecture, but would need explicit handling of source discovery, writes, subprocesses, metadata, symlinks, revision mapping, recovery and post-render authority. There is no experiment in this assessment proving that architecture equivalent or impossible.

Configuration is still the right mechanism for existing switches and channel identity. The remote-desktop patch already uses LifeOS's native isDesktopChannel helper. Merely removing TERM does not establish equivalence because tab-setter also restores persisted Kitty session state and has a cmux path. Similarly, hooks.enabled is already a configuration value, but the patched request branch is what actually honors it. Disabling the whole native service would remove behavior. Daily GitHub/Cloudflare/quota/remote-enrollment exclusions are deployment selections, not permission to delete compatibility code.

**Concrete reduction proposals, in verification and dependency order**

First establish one canonical ordered patch manifest and generate packaging copies. This changes release tooling and distribution ownership, not upstream behavior. Verify byte equality, missing-file refusal, wheel contents, source preparation and install rollback. It has the easiest equivalence oracle and the lowest runtime risk. Do not replace the packaged copies with symlinks unless wheel and installer behavior is verified on the actual distribution path.

Next separate generated static output from source patch maintenance. Use a controlled frontend builder with exact Node/Bun/package-manager versions, the existing lockfile in frozen mode, complete patched frontend inputs, strict TypeScript validation separate from Next's permissive build setting, and an explicit deterministic build identity or a documented semantic comparison. Record input and artifact hashes in the release manifest. Build twice in isolated clean directories. Compare routes, chunk references, assets and browser behavior; retain a complete versioned output archive for rollback. A deterministic build-ID change would itself be another upstream source change unless supplied through a supported build mechanism, so include it honestly in the divergence count. The verified source-only replay unblocks this work. Full build and browser equivalence remain untested proposals.

Then qualify a coherent newer Hermes revision and remove only protected-instruction-approval if the complete gates pass without it. Count 35 local behavioral patches only after that result. The newer main has changed approval and file-read internals, so partial file copying is not an acceptable shortcut. Rebase the other ten Hermes patches, audit drift in admission/retry/cancellation, and run the native tool and integration regressions together. This has higher verification difficulty and a wider blast radius than package generation or build separation.

Next submit small general correctness fixes upstream while keeping their current release implementation. Natural independent proposals are the watchdog file/schema correction, checkpoint hook honoring, combined terminal auditing, transcript tool-result correlation, YAML block handling, atomic state writes, response/issue receipt ordering, universal channel checks, array parsing/doc edit containment, native inference export reuse, web extraction classification and cron runtime launcher reuse. Split by semantics, not just patch filenames. Upstream acceptance removes divergence; combining them locally does not. There is no reliable count or acceptance forecast for these proposals.

Finally consider upstream extension contracts for required policy middleware, early prompt admission, universal stop checks, final transport authority, per-child routing, supplied native sources and transactional publication. Design the seam around a demonstrated native boundary. Keep the integration policy in this plugin. This is the largest possible long-term source-divergence reduction and also the hardest to verify because it changes where authority is enforced. Adrian should review the architecture before implementation.

A narrower optional cleanup is to use existing atomicWriteText for ConfigEvalFire instead of a local unique-temp sequence. Other patches already reuse this helper. First compare mode preservation, parent creation, failure cleanup, exclusive temp creation and concurrency. This reduces duplicated logic but does not remove the native call-site modification. Replacing the native code with a Python copy of the hook is not counted as a reduction.

Squashing 36 patches into two, folding the later LifeOS patches into memory-access, or regenerating an aggregate diff can preserve the prepared tree if verified with the same oracle. These simplify application bookkeeping only. A rebaseable integration branch can be the authoring source of truth and generate reviewable patches at release, but it still maintains the same fork. None authorizes fewer behavioral tests.

## Findings in dependency, verification, risk, and blast-radius order

### 1. Decide how correction and forgetting affect archive and historical retrieval

**Classification:** Concrete missing cross-layer contract, building on an existing correction/forget acceptance question. Decide before implementation; prove before enabling LifeOS ownership.

The design promises search of “permitted current LifeOS knowledge” and that forgetting removes a record from ordinary recall. The native hot-memory `op:set` provides a useful starting point, but it affects a whole hot file, not all sources of the claim. `MemorySystem.ts:406` reads hot entries and sends a full list to MemoryWriter. Native archive note writes at `MemorySystem.ts:622` append a dated section. `MemoryRetriever.ts:667` searches archive notes, a bounded recursive LEARNING slice, and both hot files. It labels learning hits historical at line 766, but they still enter ordinary model context. Its read path does not establish record-level supersession or forgotten-claim filtering. `MemorySystem.find` at line 888 also drops the retriever's `noteClass` distinction from returned results.

Thus a hot-memory removal or a newer appended correction alone cannot establish the promised behavior. A historical label helps interpretation but does not establish exclusion or prevent a reviewer from saving the old claim again. The current design mentions residual history copies but should explicitly say whether retained LEARNING and audit copies are permitted in default retrieval and reviewer input. It should also distinguish a deliberate later user reassertion from automatic replay of the old source.

**Smallest amendment:** Define active, superseded, forgotten, and pending semantics across hot memory, knowledge/ideas, searchable learning, and derived context. Ordinary fact recall must exclude superseded and forgotten claims even when their retained historical source still exists. An explicit history/audit operation can expose permitted historical evidence with clear status. The reviewer must honor applied corrections and forget decisions when processing older sources. Reuse native status, identifiers, and operations where they meet this contract; choose minimal store-owned metadata only if native operations cannot do it. A separate authoritative archive is unnecessary.

**Acceptance:** Save the same synthetic obsolete claim in hot memory, archive, and learning; correct it, then query every ordinary path and run a native review over the old synthetic source. Repeat with forget. Assert that the old claim does not return or reappear. Permit an explicit history query only under the selected retention policy. Then deliberately reassert the claim as a new user request and verify the documented policy. Test forgetting a single entry, several entries, a whole note, and a guarded hot-memory clear. MemoryWriter's `allowDrastic` bypass exists at line 517, but MemorySystem's public hot write does not pass it, so native guard refusal must be handled truthfully.

### 2. Bind native automatic recall to a trusted session policy before model exposure

**Classification:** Concrete missing enforcement boundary. Decide before implementation; prove before ownership in a messaging gateway with multiple participants or audiences and before sharing.

Provider and MCP permissions cannot govern a native hook that reads files directly. `MemoryTurnStart.hook.ts:95` reads session ID and prompt, invokes LoadMemory and retrieval, and writes context to stdout. It has no visible author, audience, model-route, or allowed-category filter. `LoadMemory.hook.ts:79` renders both hot files. Its parser does not receive client permissions. `MemoryRetriever.getRelevantContext` exposes type filtering, not project/principal/assistant access policy.

The design correctly distinguishes private access from public delivery, but post-generation filtering cannot undo a private memory's transmission to a model or a child's inherited context. A cached private conversation can also retain recalled content if the same agent/session is later reused under a restricted audience. Filtering only fresh hook output does not revoke memory already present in model history or a compression summary.

**Smallest amendment:** Define one host-authenticated context policy covering principal, session author, participants, conversation visibility, delivery audience, outbound destination, allowed memory categories, and selected model route. Messaging adapters supply metadata at the boundary; memory policy remains independent of the messaging app. Bind account IDs from different messaging apps to the same principal only through an approved host identity mapping; display names cannot establish that binding. Unknown or ambiguous visibility must choose the restricted default, with no private injection until authorization is established. The inspected sources do not prove that every current Hermes adapter supplies this metadata. Apply it before native hook output, explicit tool results, snapshots such as SOUL, child context, compression context, and reviewer input reach a model. Provider/MCP callers must not choose their own principal or policy through arguments. On policy reduction, participant change, destination change, or audience change, the host must discard or rebuild affected context and caches. Native retrieval caches at MemoryRetriever.ts:698 key query/options without policy, principal, or store revision, with a 60-second TTL; a future persistent shared-access process must scope results by policy and revision or invalidate safely. A per-prompt subprocess may not retain this cache across turns, so the inspected cache alone does not prove a cross-session leak. Preserve native hook ownership, cadence, and allowed-session behavior; document restricted-session filtering as an intentional behavior required by privacy. If the installed native interfaces cannot express the policy, document the smallest bridge/native extension and test it. Do not silently claim unchanged hook parity and enforced category filtering simultaneously.

**Acceptance:** Put distinctive private principal, assistant, project, and historical markers in synthetic fixtures. Capture actual model inputs across at least two messaging adapters for private direct messages, groups, public channels, threads, scheduled proactive destinations, and child tasks under allowed and denied policies. Test unknown/ambiguous visibility and approved versus unapproved cross-app principal bindings. Assert denied markers are absent before model submission. Switch a previously private cached session to a restricted policy and compress/resume it; assert prior private context does not survive. Test shared sessions with changing authors and participants, unauthorized messages, and permission changes during a session. Then verify permitted markers still arrive once through native recall. Outbound output checks apply to the actual destination for every messaging adapter, including scheduled proactive sends. Any Discord case is an example of this common policy.

### 3. Define stable references, authenticated provenance, and repeat-request semantics

**Classification:** Concrete missing interface contract; identity and repeated requests are already listed for testing. Decide the contract before implementation; prove before ownership and cross-client use.

“Return its reference and writer provenance” is a stronger promise than the inspected native interfaces provide. Hot memories are strings in two files (`MemoryTypes.ts:100`), without a visible per-entry ID. `MemorySystem.add` uses constant `updatedBy: "MemorySystem.add"` at line 434. Native archive notes receive a note ID and source session (`MemorySystem.ts:519`), but appended sections are timestamped, with source session and confidence at line 545. Neither source session nor actor selected by a client authenticates the writer. `sanitizeTypedItemForPersistence` allowlists fields at line 683, so attaching arbitrary writer fields to a request does not make them durable. `find` returns paths and excerpts, not operation receipts or stable fact revisions.

**Smallest amendment:** Specify the reference granularity: file/note plus entry or section reference, revision, and status. A correction or forget must target the referenced claim, fail or request clarification on ambiguity, and refuse stale destructive edits. Bind writer identity from Hermes session or enrolled MCP credentials, keep source provenance distinct from writer identity, and carry both into the returned receipt and supported native metadata. Define an idempotency key scoped to authenticated writer and operation, including how a retry after an uncertain response obtains the existing result. Do not equate full-list deduplication with request idempotence for append-style notes and proposals.

**Acceptance:** A saved reference remains resolvable after another hot entry is reordered or added. Two notes with the same display name remain unambiguous. A stale revision cannot modify an unrelated later entry. Retrying an acknowledged or interrupted request produces one fact/proposal and the same receipt. Client-supplied writer names cannot change authenticated provenance. Provenance survives restart and restore.

### 4. Treat atomicity and all-writer serialization as different acceptance requirements

**Classification:** Already identified implementation acceptance work with additional concrete native cases. State the invariant before implementation; establish it before ownership, including when remote sharing remains off.

The design already flags stale-list replacement. This matters locally too: native reviewers and explicit provider writes can overlap. `MemorySystem.addMemoryItem:407` reads outside MemoryWriter's lock; `MemoryWriter.ts:556` locks publication without an expected-revision option. A fully atomic rename can publish a stale list successfully. A provider-only mutex does not serialize a direct native reviewer process.

Additional native paths expand the test matrix. `MemorySystem.addNoteTypeItem:623` checks existence before append locking, so simultaneous creation must be tested. Its related-link read/write at lines 635-639 follows the locked content append and uses direct writeFileSync, so the combined operation is not visibly one transaction. Native hot locks at `MemoryWriter.ts:353` differ from Tier B's stamped lock recovery at `MemorySystem.ts:215`. `MemoryReviewFire.hook.ts:247` reads cadence state and later writes it without visible cross-session exclusion; `spawnReviewer:218` launches a detached subprocess. These are concurrency exposures, not proof that data loss or duplicate reviewers occurred in practice.

**Smallest amendment:** Require each acknowledged logical operation to retain other committed changes, including native hook/reviewer operations. Choose native read-modify-write inside the lock or expected-revision conflict detection with bounded safe retry. All writers must use the same mechanism; a remote wrapper lock alone is insufficient. Specify content plus metadata commit semantics and separate contention, stale lock, unknown outcome, and rejection results. Do not blindly remove a lock on age while a writer may still be alive.

**Acceptance:** Deterministically interleave two hot additions, correction versus addition, forget versus reviewer curation, two native reviewers, simultaneous archive note creation, and related-link merge versus append. Assert both acknowledged changes survive or one returns an explicit conflict. Kill a synthetic writer at each publication boundary, restart, and verify recoverable state. Test stale-lock recovery and live-lock refusal for hot and archive paths. Repeat operation retries after an unknown result.

### 5. A successful native call must not imply that the requested fact was saved

**Classification:** Already required truthful saving, with a concrete result-mapping gap. Prove before ownership.

Native MemoryWriter validation can drop malformed, overlength, and duplicate entries while returning success for the accepted list (`MemoryWriter.ts:184`, `:541`, `:623`). Its hot caps are 48 entries and 256 content characters (`:64`). MemorySystem returns dropped counts but not an identity for each accepted requested claim (`MemorySystem.ts:442`). A candidate absent after validation must not become a “saved” receipt. Scope-based proposals may become an upgrade rather than a proposal (`MemorySystem.ts:343-357`), so “queued” must describe the actual destination and status. MemoryReviewFire records spawn success and updates cadence at lines 260-267; spawning alone proves neither reviewer completion nor accepted writes.

**Smallest amendment:** Use explicit committed, unchanged/idempotent, pending, rejected, and unknown outcomes. Include the reference/revision, accepted change, and reason for any dropped or deferred portion. A save status requires verification of the requested mutation; reviewer health distinguishes attempted, running, completed, and failed. Partial acceptance is allowed only when its extent is shown. Never evict unrelated facts silently to satisfy a cap.

**Acceptance:** Submit malformed and overlength hot entries, exact duplicate, cap overflow, guarded shrink, mixed accepted/rejected list, redirected proposal, reviewer spawn failure, reviewer model failure, and post-commit response loss. Assert the user and both interfaces report actual state with no false saved result. Verify valid duplicate requests report unchanged or the prior receipt rather than invented new facts.

### 6. Pin installation, provider lifecycle, and recovery as one ownership gate

**Classification:** Mostly already stated acceptance work; sufficient design, add explicit cases. Prove before enabling ownership.

The installed Hermes supports the direction. Provider discovery reads user/project plugin directories or package entry points (`plugins/memory/__init__.py:65-118`). A hook plugin's installation does not by itself prove discovery of a provider name. Tool injection is gated by the memory toolset (`agent/memory_manager.py:79-140`). Agent initialization independently controls built-in stores and provider activation (`agent/agent_init.py:1306-1386`), and passes profile home, platform, identity, and gateway attributes (`:1267-1303`). The native files copied here derive paths from homedir plus `.claude`; “use the installed paths” needs real profile/separate-root evidence rather than an assumption that Hermes's profile home redirects native code automatically.

The design already correctly preserves Hermes skill review and names child, cron, compression, restart, failure, and updates. Retain these as required gates, with no claim that reading the provider ABC establishes runtime behavior. A no-op provider recall/extractor is appropriate when native hooks own those tasks. The compression checkpoint contract must be truthful: a no-op provider must not claim it durably checkpointed conversation memory. Hermes retains history; LifeOS need not copy whole conversations just to implement the provider interface.

**Smallest amendment:** Record a tested manifest covering Hermes/provider API, plugin, LifeOS/native schema, optional MCP component, and dependencies. Test installed provider discovery and tool naming on a completely fresh server/profile. Define readiness separately for provider tools, hooks, native storage, and reviewer. Preserve built-in files while disabling both built-in writes and injection; an unavailable provider must show unavailable memory and must never enable a silent fallback. Backups must capture authoritative files and necessary IDs, revisions, policy/status/provenance metadata, and pending work consistently with writers. Treat rendered SOUL, recall caches, cadence state, and compression-derived context as refreshable derived data. Unsupported schema versions must fail explicitly before writes. Quiesce active writers during restore/update or prove compatible transaction behavior.

**Acceptance:** Fresh install discovers the configured provider and enabled tools without `.211`/`.213`; profiles do not read each other's LifeOS roots. Verify new, resume, branch, reset, rewind, compression, gateway rebuild, shared-author turn, child, cron, and flush contexts. Assert extraction is not duplicated and skills still learn. Remove a dependency or make the store/provider unavailable: no false health, no built-in fallback writes/injection, and conversation behavior follows documented native hook failures. Restore a synthetic backup while a reviewer is pending, restart, and verify facts/references/status plus refreshed context. Rehearse supported update and rollback; reject an unsupported schema without altering memory. Test disk full, permissions, missing/broken USER_DATA symlink, and recoverable corrupt state. The native `assertInsideUserData` check at `MemorySystem.ts:841` makes that boundary a concrete fresh-install requirement.

### 7. Specify the restricted SSH execution boundary before enabling sharing

**Classification:** Existing design direction needing enrollment acceptance detail. Resolve and prove before sharing; it need not block initial local implementation.

Per-client revocable SSH keys and read-first grants are the right default. They enforce memory policy only if the key can execute only its bound MCP command, with a policy bound by the server. An unrestricted shell, forwarded service, writable policy file, arbitrary environment/root override, or another key for the same identity can bypass the intended grant. The design already acknowledges filesystem bypass and unknown downstream model routes. Do not present a declared route as technically verified.

**Smallest amendment:** Enrollment binds a key to a server-controlled client ID and allowed operation/category policy. A forced command ignores untrusted command arguments and controls root/environment. Disable shell, PTY, forwarding, and unrelated subsystem access for this credential. Describe isolation actually achieved with the chosen account permissions. Define revocation of active as well as future MCP sessions, and recheck policy at each operation. Read results include only permitted references/excerpts and omit denied metadata. Proposal creation and proposal approval are separate grants; a project writer cannot promote a behavioral rule or modify principal identity. Reuse the existing MCP's maintained policy/protocol if it supports these invariants; confirm its dependency/schema requirements on a clean install without existing deployed addresses or caller names.

**Acceptance:** Connect two enrolled clients with different categories. Try spoofed caller names, principal writes, proposal approval, raw path traversal, environment overrides, shell/subsystem access, and forwarding. Verify policy denies each prohibited operation. Revoke one active client and attempt another read/write over its existing connection. Reenroll with a new key and verify the old key remains revoked. Verify no denied memory reaches a subprocess/model route or returned result. Confirm the read-only default and remote-disabled state after installation, restore, and upgrade.

## Optional additions that do not block the accepted scope

Vector search, a new database, public HTTP transport, cross-install federation, automatic reconciliation with existing production stores, and new background extraction are unnecessary for this request. A richer audit/history browser can follow later; the first version still needs honest residual-copy reporting and stable references. Importing old Hermes data remains separately authorized work. General protection from an arbitrary local process with the same operating-system permissions remains outside an MCP-only guarantee and must be stated accurately.

## Review focus

The largest risk is assuming the provider and MCP access layer governs native hook context and reviewer writes. The next risk is satisfying hot-memory correction while ordinary archive/learning recall still returns the old claim. Resolve these contracts first, then use deterministic synthetic tests to decide the minimum native extension. No runtime guarantees or acceptance passes are claimed by this review.

# LifeOS hook parity record

This record describes the public LifeOS hook settings installed from commit `5e2f2e8` on 2026-09-27. It distinguishes registered callbacks from verified behavior. The bridge is a Hermes plugin. It does not edit LifeOS source files.

## Event coverage

| Claude Code event | Registrations | Hermes path | Current result |
| --- | ---: | --- | --- |
| `PreToolUse` | 6 | `pre_tool_call` | Command and local HTTP hooks execute for mapped tools. Exit code 2 and deny decisions block. Updated input maps back to Hermes arguments. |
| `PostToolUse` | 32 | `augment_tool_result` | Hooks execute after the existing result transform. Their `additionalContext` is appended to the model-bound result. |
| `UserPromptSubmit` | 9 | `pre_llm_call` | Hooks execute on text and multimodal prompts. For multimodal content, the hook receives the text portions joined with newlines. Their context is added to the current user turn. Async hooks start without blocking. |
| `Stop` | 8 | `pre_turn_stop` | Hooks execute on each text answer. A block continues the same Hermes turn, up to eight consecutive times by default. `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP` overrides the cap. A private transcript supplies `transcript_path`. |
| `SessionStart` | 5 | first `pre_llm_call` | Hooks execute before the first user prompt is sent to the model. Their text output joins that prompt's context. Hermes's first-turn flag supplies `source: startup` or `source: resume`; a persisted transcript supplies the fallback when that flag is absent. |
| `SessionEnd` | 6 | `on_session_finalize` | All six installed handlers completed successfully on a synthetic session boundary. The native SessionCleanup hook removed a synthetic session-name entry while preserving unrelated entries. Other state-changing effects need separate checks. |
| `PostToolUseFailure` | 3 | `augment_tool_result` on tool error | The failure payload is tested with a real child process. |
| `PermissionRequest` | 2 | `pre_command_approval` for Bash and `pre_tool_call` for files and MCP | Native `Safety.hook.ts` can grant a recoverable dangerous-command warning in Hermes manual mode and after smart mode guardian escalation. Hermes hardline, user deny, and Tirith warnings remain effective. For Write, Edit, and MCP, a native grant proceeds; a neutral decision requests human review, and a deny blocks. Hermes file guards still apply after a grant. If Hermes itself will prompt for an SSH config write, the bridge defers a neutral LifeOS review to that guard so the user gets one prompt. |
| `TaskCreated` | 1 | `pre_tool_call` and `post_tool_call` on `todo_list` and `kanban_create` | With the LifeOS compatibility patch, the native hook receives the Hermes session count and decides each new task. The bridge reserves slots before a call and commits them only after success. Without that patch, the bridge keeps an equivalent policy fallback. |
| `ConfigChange` | 1 | bridge file watcher while a session is active | Installed user, project, local, and file-based managed settings plus user and project skills are checked once a second. Project roots follow observed session working directories. Project changes reach only sessions using that project, with the changed project as `cwd`. Native hooks receive `source`, `file_path`, and LifeOS's `config_path` alias. A block keeps the active user hook settings. |
| `StopFailure` | 1 | `api_request_error` plus `on_turn_result` | Terminal API errors run the native log hook once with the last API error. Direct error returns and exhausted retries are covered. An earlier recovered API error does not turn an unrelated local failure into StopFailure. |

The native bridge executes the installed registration types with partial coverage of `ConfigChange` and Bash `PermissionRequest`. The MCP `PermissionRequest` registration executes, but Hermes's trusted-server policy can still differ from Claude Code's permission rules. Write and Edit permissions now execute the native hook, but Hermes file guards and a multi-file patch's approval scope can differ from Claude Code. For new Hermes todo IDs and kanban task calls, the patched native `TaskCreated` hook now runs with session-owned counts. The bridge retains a policy fallback for unpatched LifeOS installs. This is an event-level mapping, not a count of passing behavioral tests. Hermes tool names currently mapped are `terminal`, `read_file`, `write_file`, `patch`, `clarify`, `delegate_task`, `web_search`, `web_fetch`, `skill_view`, `tool_search`, and `mcp__*`. Hermes `clarify` maps to Claude Code `AskUserQuestion` for the installed tab-state hooks. Claude Code `MultiEdit` has no exact Hermes tool mapping. Batched Hermes delegation now runs the `Agent` hooks per child with a description, prompt context, background state, and explicit model when supplied; Hermes has no matching Claude subagent type, so the bridge labels each child `general-purpose`. Local Pulse routes fail open when Pulse is not running, as they do in Claude Code. Project hook registrations load only from roots in Hermes's `skills.trusted_project_dirs`. User, project, and local hook groups run in that order for the matching project session.

## Hermes core dependency

The stock Hermes plugin API cannot continue a non-coding turn from a Stop hook. It also keeps only the first tool-result replacement, so the existing LifeOS sidecar can mask another plugin's `additionalContext`. Its approval hooks observe requests but cannot grant one. The test fork adds four generic plugin events: `pre_turn_stop`, `augment_tool_result`, `pre_command_approval`, and `on_turn_result`. It also preserves updated tool arguments when a plugin requests approval. The [patch](../patches/hermes-hook-controls.patch) was made against Hermes commit `758ad514e` and includes its tests. It also applied cleanly to public Hermes HEAD `bac0c45d8` on 2026-09-27, where 116 focused tests passed. The bridge's native task and watchdog probes passed against that newer checkout. Review and test the patch on any later Hermes revision before enabling this plugin. The isolated dashboard remains on branch `feature/universal-stop-hook` at commit `4d5cff483`; production Hermes is unchanged.

## Current limits

- Full hook parity is not achieved. Native `TaskCreated` execution requires the separate [LifeOS compatibility patch](../patches/lifeos-task-governance.patch), based on LifeOS `5e2f2e8`. An unpatched install uses the bridge policy fallback. In smart approval mode, a native grant applies only after the guardian escalates. A guardian denial and Tirith finding still require human review. For SSH config writes, a neutral LifeOS decision defers to Hermes's existing file guard. Other LifeOS review requests still use the plugin approval gate.
- Config changes are detected within the watcher's one-second polling interval while a session is active, rather than through a filesystem event. The watcher stops when no session remains. Project roots are registered when a session or local tool enters them; a remote or container tool's filesystem is not watched. File-based managed policy paths are audited but Hermes does not apply Claude Code's managed settings. Server-managed settings, macOS managed preferences, and Windows registry policy have no bridge event.
- Project and local hook registrations require an explicitly trusted Hermes project root. Project `env` values apply to matching hook processes. The bridge does not apply Claude Code permission rules. It finds a Git repository root or a non-Git ancestor with `.claude/settings.json` or `.claude/settings.local.json`, stopping before the user's home directory. A single session's tool calls into two repositories selected the matching hook groups in a local test; other session-level behavior across repositories remains unverified.
- A successful Hermes multi-file patch is presented to `Edit` PreToolUse, PermissionRequest, and PostToolUse hooks once per changed, deleted, or moved path. Added and updated files include added lines as `new_string` and removed lines as `old_string`; the bridge cannot reconstruct full file contents or unchanged context from a patch. Relative file paths are made absolute against the task workspace without dereferencing symlinks. Its private transcript records one Claude-shaped `Edit` tool use and matching result per path, which lets LifeOS transcript readers find each path. A failed patch produces one PostToolUseFailure event and one transcript tool call with the original Hermes patch shape. Hook `cwd` follows Hermes's task workspace for a local backend and an explicit terminal `workdir` when supplied. Remote or container backends and symlinked workspaces still need separate path fidelity tests.
- The bridge creates a private Claude-shaped transcript from the events it sees. It is sufficient for the tested Stop gates, but it is not a byte-for-byte Claude Code transcript. Hook behavior that depends on Claude-specific transcript entries needs separate verification.
- The checkpoint compatibility patch requires a subject prefix shorter than 50 characters. A criterion in a project with an exceptionally long slug remains pending, with an error, instead of creating a nonconforming commit. It also leaves a failed commit's staged files for operator review, as Git normally does.
- Hermes terminal results expose one combined `output` field. The LifeOS terminal audit patch records that output accurately, but cannot separate stdout from stderr. Hooks that require the individual streams still need a Hermes terminal result change.
- Multimodal prompts pass text portions to UserPromptSubmit. Image and attachment content remains in the bridge transcript but is not represented in the prompt string, so hooks that interpret that content can differ from Claude Code.
- Async LifeOS hooks run through a detached child process with a private spool file so a one-shot Hermes process can exit without truncating their input. Up to 64 KiB of context output per hook is delivered at the next prompt for the same session. Completed output is removed after delivery or session finalization. A service manager that kills an entire process group or control group can still stop the child.
- LifeOS's nested inference tool clears local gateway variables. The optional `lifeos_hook_bridge/bin/claude` child launcher restores private gateway settings and maps LifeOS's four model tiers to one configured local model at three supported effort settings. The local gateway rejected LifeOS's requested `high` effort; `xhigh` worked. This cannot reproduce four distinct model tiers with a single local model. The launcher still requires the Claude Code CLI as a child helper; Hermes remains the main conversation agent. See [the measured effort mapping](../notes/2026-09-27-local-model-effort.md).
- The native watchdog needs the separate [LifeOS watchdog patch](../patches/lifeos-agent-watchdog.patch). Hermes notification preferences can suppress its alerts. Its process and route were tested with a synthetic Discord destination, but actual Discord delivery is unverified on `.212`. See [the watchdog record](../notes/2026-09-27-agent-watchdog.md).
- The isolated test account uses LAN-only outbound rules. The plugin does not install a firewall or credentials. Pulse runs on loopback and is not part of the plugin installation.

## Test installation

The test account has a fresh LifeOS tree and a `~/.claude/settings.json` created by `InstallHooks.ts --apply`. The plugin files live under `~/.hermes/plugins/lifeos-hook-bridge/`, and `hermes plugins enable lifeos-hook-bridge` enables them. The existing LifeOS sidecar guard remains enabled. The private `~/.config/lifeos-hook-bridge/model.env` file supplies the local model gateway to the child launcher and has mode `0600`. Keep that file outside Git.

The core patch applies only to a compatible Hermes checkout. On a new branch, run `git apply --check /path/to/lifeos-hermes-plugin/patches/hermes-hook-controls.patch` from the Hermes checkout, then apply it and run the included tests. Do not apply the patch to an unrelated Hermes version without reviewing the changed call sites.

# LifeOS hook parity record

This record describes the public LifeOS hook settings installed from commit `5e2f2e8` on 2026-09-27. It distinguishes registered callbacks from verified behavior. The bridge is a Hermes plugin. It does not edit LifeOS source files.

## Event coverage

| Claude Code event | Registrations | Hermes path | Current result |
| --- | ---: | --- | --- |
| `PreToolUse` | 6 | `pre_tool_call` | Command and local HTTP hooks execute for mapped tools. Exit code 2 and deny decisions block. Updated input maps back to Hermes arguments. |
| `PostToolUse` | 32 | `augment_tool_result` | Hooks execute after the existing result transform. Their `additionalContext` is appended to the model-bound result. |
| `UserPromptSubmit` | 9 | `pre_llm_call` | Hooks execute before the current prompt enters the bridge transcript. A block prevents model processing and discards the current prompt from bridge and Hermes history. For multimodal content, the hook receives the text portions joined with newlines. Allowed hook context is added to the current user turn. Async hooks start without blocking. |
| `Stop` | 8 | `pre_turn_stop` | Hooks execute on each text answer. A block continues the same Hermes turn, up to eight consecutive times by default. `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP` overrides the cap. A private transcript supplies `transcript_path`. |
| `SessionStart` | 5 | first `pre_llm_call` | Hooks execute before the first user prompt is sent to the model. Their text output joins that prompt's context. Hermes's first-turn flag supplies `source: startup` or `source: resume`; a persisted transcript supplies the fallback when that flag is absent. |
| `SessionEnd` | 6 | `on_session_finalize` | Handlers run concurrently, matching Claude Code's hook contract. All six installed handlers completed successfully on a synthetic session boundary. A real one-shot Hermes CLI shutdown also reached a temporary native SessionEnd hook. | `PermissionRequest` | 2 | `pre_command_approval` for Bash and `pre_tool_call` for files and MCP | Native `Safety.hook.ts` can grant a recoverable dangerous-command warning in Hermes manual mode and after smart mode guardian escalation. | `TaskCreated` | 1 | `pre_tool_call` and `post_tool_call` on `todo_list` and `kanban_create` | With the LifeOS compatibility patch, the native hook receives the Hermes session count and decides each new task. Native hooks receive `source`, `file_path`, and LifeOS's `config_path` alias. A block keeps the active user hook settings. |
| `StopFailure` | 1 | `api_request_error` plus `on_turn_result` | Terminal API errors run the native log hook once with the last API error. Direct error returns and exhausted retries are covered. An earlier recovered API error does not turn an unrelated local failure into StopFailure. |

The native bridge executes the installed registration types with partial coverage of `ConfigChange` and Bash `PermissionRequest`. The MCP `PermissionRequest` registration executes, but Hermes's trusted-server policy can still differ from Claude Code's permission rules. Write and Edit permissions now execute the native hook, but Hermes file guards and a multi-file patch's approval scope can differ from Claude Code. For new Hermes todo IDs and kanban task calls, the patched native `TaskCreated` hook now runs with session-owned counts. The bridge retains a policy fallback for unpatched LifeOS installs. This is an event-level mapping, not a count of passing behavioral tests. Hermes tool names currently mapped are `terminal`, `read_file`, `write_file`, `patch`, `clarify`, `delegate_task`, `web_search`, `web_fetch`, `skill_view`, `tool_search`, and `mcp__*`. Hermes `clarify` maps to Claude Code `AskUserQuestion` for the installed tab-state hooks. Claude Code `MultiEdit` has no exact Hermes tool mapping. Batched Hermes delegation now runs the `Agent` hooks per child with a description, prompt context, background state, and explicit model when supplied; Hermes has no matching Claude subagent type, so the bridge labels each child `general-purpose`. Local Pulse routes fail open when Pulse is not running, as they do in Claude Code. Project hook registrations load only from roots in Hermes's `skills.trusted_project_dirs`. User, project, and local hook groups run in that order for the matching project session.

## Hermes core dependency

The stock Hermes plugin API cannot continue a non-coding turn from a Stop hook. It also keeps only the first tool-result replacement, so the existing LifeOS sidecar can mask another plugin's `additionalContext`. Its approval hooks observe requests but cannot grant one. It treats `pre_llm_call` results only as context and cannot reject a user prompt. The test fork adds four generic plugin events: `pre_turn_stop`, `augment_tool_result`, `pre_command_approval`, and `on_turn_result`. It also preserves updated tool arguments when a plugin requests approval and honors a `pre_llm_call` block before model processing or turn persistence. The [patch](../patches/hermes-hook-controls.patch) was made against Hermes commit `758ad514e` and includes its tests. The updated patch applied cleanly to public Hermes HEAD `9a0a1625` on 2026-09-27. Its changed Python files compiled, and 153 focused tests passed in a disposable checkout on `.212`. The installed `.212` fork passed 37 focused tests. See [the upstream patch check](../notes/2026-09-27-upstream-patch-check.md). Review and test the patch on any later Hermes revision before enabling this plugin. The isolated dashboard remains on branch `feature/universal-stop-hook` at commit `5722a259f`; production Hermes is unchanged.

## Current limits

- Full hook parity is not achieved. Native `TaskCreated` execution requires the separate [LifeOS compatibility patch](../patches/lifeos-task-governance.patch), based on LifeOS `5e2f2e8`. All six LifeOS patches applied to public HEAD `5e2f2e8` on 2026-09-28. Six native task, watchdog, audit, and checkpoint tests passed against the patched fresh checkout, as did the FailureCapture transcript and remote desktop gate tests. See [the upstream LifeOS patch check](../notes/2026-09-27-lifeos-upstream-patches.md). An unpatched install uses the bridge policy fallback. In smart approval mode, a native grant applies only after the guardian escalates. A guardian denial and Tirith finding still require human review. For SSH config writes, a neutral LifeOS decision defers to Hermes's existing file guard. Other LifeOS review requests still use the plugin approval gate.
- Config changes are detected within the watcher's one-second polling interval while a session is active, rather than through a filesystem event. Its fingerprint now includes change time and file identity, so a same-size rewrite with preserved modification time reaches the hook and reloads active settings on `.212`. The watcher stops when no session remains. Project roots are registered when a session or local tool enters them; a remote or container tool's filesystem is not watched. File-based managed policy paths are audited but Hermes does not apply Claude Code's managed settings. Server-managed settings, macOS managed preferences, and Windows registry policy have no bridge event. See [the fingerprint regression](../notes/2026-09-28-config-fingerprint.md).
- Project and local hook registrations require an explicitly trusted Hermes project root. Project `env` values apply to matching hook processes. The bridge does not apply Claude Code permission rules. It finds a Git repository root or a non-Git ancestor with `.claude/settings.json` or `.claude/settings.local.json`, stopping before the user's home directory. An isolated `.212` process with two temporary trusted repositories sent tool events through one session and selected each repository's matching hook without cross-routing. Remote and container project hook registration remains untested. See [the project routing record](../notes/2026-09-27-project-routing.md).
- A successful Hermes multi-file patch is presented to `Edit` PreToolUse, PermissionRequest, and PostToolUse hooks once per changed, deleted, or moved path. Added and updated files include added lines as `new_string` and removed lines as `old_string`; the bridge cannot reconstruct full file contents or unchanged context from a patch. File paths use Hermes's task path resolver, which follows local symlinks and preserves remote or container namespace rules. Its private transcript records one Claude-shaped `Edit` tool use and matching result per path, which lets LifeOS transcript readers find each path. A failed patch produces one PostToolUseFailure event and one transcript tool call with the original Hermes patch shape. Hook `cwd` follows Hermes's task workspace for a local backend and an explicit terminal `workdir` when supplied. The bridge and Hermes resolved the same relative path under simulated SSH and Docker task namespaces on `.212`. A live SSH read and write to a disposable account confirmed that Hermes's target path matches the bridge path. Native file-reading hook effects on that remote filesystem and container file operations remain unverified. See [the simulated path record](../notes/2026-09-27-remote-file-paths.md) and [the live SSH probe](../notes/2026-09-28-live-ssh-file-paths.md).
- The bridge creates a private Claude-shaped transcript from the events it sees. It is sufficient for the tested Stop gates, but it is not a byte-for-byte Claude Code transcript. Hook behavior that depends on Claude-specific transcript entries needs separate verification.
- A failed checkpoint commit leaves its staged files for operator review, as Git normally does. A long project slug no longer prevents the checkpoint; the commit body retains the full marker for LifeOS lookup.
- Hermes terminal results expose one combined `output` field. Its environment layer merges stderr into stdout before the terminal tool returns. The installed LifeOS EventLogger is the only current hook that inspects terminal stream fields, and the LifeOS terminal audit patch records combined output accurately. Separate streams remain unavailable to any future hook that requires them; that would need a Hermes terminal execution change. See [the stream audit](../notes/2026-09-27-terminal-stream-audit.md).
- Multimodal prompts pass explicit text blocks to UserPromptSubmit. Image and attachment content remains in the bridge transcript. The [Claude Code hook contract](https://code.claude.com/docs/en/hooks#userpromptsubmit-input) defines `prompt` as the text the user submitted, and the installed LifeOS hooks that read `prompt` treat it as a string. A three-block text, image, text prompt produced the same newline-joined text in native Claude Code and the bridge on `.212`. Both supply an empty prompt string for an image-only message. A regression also excludes `input_image` and `input_file` payloads that carry a `content` field; the prior extractor passed those bytes to the native hook. Other attachment shapes and pasted-content markers remain unverified. See [the multimodal prompt record](../notes/2026-09-27-multimodal-prompt-shape.md).
- Async LifeOS hooks run in separate transient user services when systemd is available. The bridge falls back to a detached child when it is not. A private spool file supplies input and environment after the Hermes parent exits. Up to 64 KiB of context output per hook is delivered at the next prompt for the same session. Completed output is removed after delivery or session finalization. Service managers other than systemd have not been tested for child survival.
- LifeOS's nested inference tool clears local gateway variables. The optional `lifeos_hook_bridge/bin/claude` launcher restores private gateway settings and maps LifeOS's four model tiers to one configured local model at three supported effort settings. With `LIFEOS_CHILD_INFERENCE_DIRECT=1`, its direct adapter sends text and image file requests to an Anthropic Messages compatible gateway without starting Claude Code. The `.212` gateway accepted all three effort values, and native LifeOS inference returned `READY` at all four requested levels plus one image file request. A single model still cannot reproduce four distinct model tiers, and LifeOS reports a name-based downgrade at every level. `CarrierProbe.ts` deliberately tests Claude Code subagent dispatch and remains Claude-specific. See [the direct inference probe](../notes/2026-09-28-direct-child-inference.md).
- The isolated `.212` gateway's `/v1/models` endpoint advertised only `flashnext-w4a16-fp8ple` on 2026-09-28. The gateway inventory confirms that distinct model-tier parity cannot be tested with the current local model supply. No gateway credential was printed or added to this repository.
- The native watchdog needs the separate [LifeOS watchdog patch](../patches/lifeos-agent-watchdog.patch). Hermes notification preferences can suppress its alerts. Its process and route were tested with a synthetic Discord destination, but actual Discord delivery is unverified on `.212`. See [the watchdog record](../notes/2026-09-27-agent-watchdog.md).
- The isolated test account uses LAN-only outbound rules. The plugin does not install a firewall or credentials. Pulse runs on loopback and is not part of the plugin installation.

## Test installation

The test account has a fresh LifeOS tree and a `~/.claude/settings.json` created by `InstallHooks.ts --apply`. The plugin files live under `~/.hermes/plugins/lifeos-hook-bridge/`, and `hermes plugins enable lifeos-hook-bridge` enables them. The existing LifeOS sidecar guard remains enabled. The private `~/.config/lifeos-hook-bridge/model.env` file supplies the local model gateway and enables direct child inference; it has mode `0600`. Keep that file outside Git.

The core patch applies only to a compatible Hermes checkout. On a new branch, run `git apply --check /path/to/lifeos-hermes-plugin/patches/hermes-hook-controls.patch` from the Hermes checkout, then apply it and run the included tests. Do not apply the patch to an unrelated Hermes version without reviewing the changed call sites.

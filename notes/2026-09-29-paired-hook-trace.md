# Paired installed hook traces

Date: 2026-09-29. The native reference is Claude Code 2.1.272 in `lifeos-claude-ref` on `.212`. The Hermes side uses the patched source and plugin in `lifeos-plugin-install-probe`. Both accounts have fresh, synthetic LifeOS data and use the same private LAN model. The LifeOS source is pinned to `5e2f2e8`.

`scripts/paired_hook_trace.py` wrapped the 72 command registrations in each installed `settings.json`. It left the two HTTP registrations unchanged. The wrapper forwarded input, output, and exit code and wrote private JSONL traces. Both original settings files were restored after the study. The raw traces stay on `.212` because they can contain prompt and hook text.

The [sanitized ledger](../docs/parity/paired-live-coverage.json) contains the observed registration IDs, exit codes, output presence, and source trace hashes. The paired sessions cover 62 of 74 registrations with no dispatch or output-shape mismatch. This is a transport check, not a side-effect verdict. Twelve registrations remain unobserved in matched live event cases.

The Bash pair ran `printf PAIR_BASH_212` through each harness. Both tools returned the marker. The Read pair read a file containing `PAIR_READ_212`. Both tools returned that marker. The Write pair created `PAIR_WRITE_212` through native `Write` and Hermes `write_file`; both resulting files contained the marker. The Edit pair changed that marker to `PAIR_EDIT_212` through native `Edit` and Hermes `patch`; both resulting files contained the new marker. Hermes needed its temporary single-query approval setting set to `approve`, comparable to the native CLI's `--allowedTools Write`. That setting was restored after the paired runs.

An earlier simultaneous Write attempt was not a valid comparison. Native LifeOS's safety classifier timed out and denied the action. Hermes refused an attempted write inside `.claude` under `HERMES_WRITE_SAFE_ROOT`. Reading `LIFEOS/HERMES/Mount.ts` showed that the LifeOS sidecar intentionally keeps the mounted tree read-only and uses its memory API for persistence. Ordinary project writes belong in the permitted workspace. A second native Write succeeded after the classifier recovered.

One Read run produced different final prose in Claude Code and Hermes. The native final response met the LifeOS voice closer format. The Hermes response did not, so `VoiceCompletion.hook.ts` logged a fallback. The ledger marks that Stop sample as incomparable input and uses the matched Bash response to compare the Stop handler. This observation may reflect different agent prompts or model output, and needs a separate output-format test before any host change.

The first nested SSH test reported a missing transcript because its assertion used the former shared `.hermes/LIFEOS` path. The actual transcript existed under the separate `.claude/LIFEOS` root and contained the nested Read event. The assertion now uses `LIFEOS_DIR` or the installed default. The corrected SSH test and three Docker file and hook tests passed on `.212`.

The full remote gate initially stopped on test fixture assumptions. The disposable SSH project had no `.claude` directory, the ISA file retained an edit from an earlier run, and the SSH cache probe selected `probe_only=True`, which disables cache synchronization. The tests now create their project directory, initialize the ISA, and stage the cache file on the remote target. The [remote gate runner](../scripts/run_live_remote_gate.py) then passed 19 SSH and Docker tests in 57.472 seconds with no selected skip. The probe used loopback SSH and the existing local `composer:2.8` image. Its raw log stays on `.212`.

The paired runs also covered failed Read, Agent delegation, Skill and Agent HTTP guards, Bash and MCP permission requests, an MCP result, a live settings change, and an interactive question. The Agent child returned the synthetic marker on both sides. Both MCP tools returned `PAIR_MCP_212`. Both interactive question handlers ran before and after the answer. The settings change modified an existing `settings.json` during a running tool call, then restored the original bytes.

The Bash permission pair exposed a real bridge gap. Claude Code in default mode invoked `PermissionRequest` for `echo PAIR_PERMISSION_212; echo exit=$?`, even though its settings allowed `Bash(echo:*)`. Hermes skipped the hook because its Bash permission parser treated each echo as allowed. Tree-sitter parsed `$?` as `simple_expansion`. The bridge now treats that node as requiring review. Its regression failed before the change and passed after it; a live Hermes turn then invoked the same `PermissionRequest` registration and executed the command. The test account's approval setting was temporarily set to `deny` to avoid automatic approval hiding the decision.

The remaining registrations are `WebFetch`, `WebSearch`, `ToolSearch`, seven `MultiEdit` handlers, `TaskCreated`, and `StopFailure`. Claude Code 2.1.272 rejected a LAN-only `WebFetch` before `PostToolUse` because it could not verify the private IP as safe. Its print-mode tool list had no `MultiEdit`, `TaskCreate`, or `ToolSearch`. Enabling task tracking in print mode did not expose `TaskCreate`; an interactive task request also found no such tool. A local MCP server with 100 tools still did not expose native `ToolSearch`. No external WebSearch request was made from this private test account. These are observed fixture limits, not proof that those hooks cannot run in every Claude Code installation.

For `StopFailure`, a loopback Anthropic-compatible server returned 503, then 400, then 401. Claude Code retried 503 beyond a 90-second cap and 401 beyond a 45-second cap. The 400 request returned `API Error: 400 PAIR_FAILURE_212`, but did not invoke the installed `StopFailure` hook. The handler remains unpaired. The failure server consumed request bodies without logging or forwarding them.

The [full release gate](2026-09-29-release-gate.md) ran and remains blocked. The paired ledger does not establish complete registration parity while twelve registrations lack native event controls.

# 2026-10-03: Hermes-managed plugin installation and updates

Adrian asks how users can install and update the complete LifeOS integration from Hermes. This note records read-only source inspection and a scanner experiment. The running `.212` installations do not change.

Hermes already has Git and catalog installation, immutable commit pins, managed dependency preparation, update checks, and plugin updates. The installed test source supports subdirectory installs, so the existing `lifeos_hook_bridge/` runtime directory is a valid package boundary. A root manifest or repository restructure is not required merely to make that directory installable.

The current runtime directory fails the actual Hermes install scanner. `tools.plugin_guard.scan_plugin` reports 48 findings, including 16 critical `ssh_backdoor` matches. `should_allow_plugin_install` returns false with both `force=False` and `force=True`. The earlier deployment record identifies scanner findings, but the impact is wider than catalog admission: they block the normal installer. Direct operator deployment explains why the installed runtime works despite this refusal. The README claim that the runtime directory passes the scanner describes an earlier revision and must be corrected before the next release.

The patched host also has a capability-probe defect. `plugin_validate.RecordingContext.register_middleware` does not accept `required`, while the actual plugin manager does. The plugin manifest declares hooks but needs a review of its middleware and command declarations. Scanner admission and capability validation are separate gates.

The bridge has authenticated dashboard controls for fresh LifeOS installation, finalization, a tested Hermes source extension, and native LifeOS updates. Its CLI exposes only `lifeos-infer` and `lifeos-probe`. It has no CLI management workflow or bridge self-update control. The existing LifeOS worker updates the native tree, not the bridge package or Hermes source. The shared-root Discord fixture requires a separate operator transaction. The host extension requires a specific clean source checkout and Linux user services; packaged and newer Hermes installations remain unsupported by that extension path.

The recommended release work has one acceptance goal: install a published integration release and update it to a later published release entirely from Hermes, with dependencies, retained user data, restart recovery, and rollback verified. Use Hermes's native plugin installer for initial discovery and package admission. Keep a reviewed release descriptor for the bridge commit, upstream source revisions, patch hashes, and supported host capabilities. Expose the coordinated integration transaction through Hermes CLI and the LifeOS dashboard. Chat-triggered actions need verified owner authority rather than fabricated account headers or arbitrary model arguments. A detached worker must survive the gateway and dashboard restart and retain a readable operation result.

The acceptance gate needs a clean stock profile, an actual Git installer run with scanning enabled, a real second-release update, failed dependency resolution, interruption during replacement, recovery, later user data, and version rollback. Both `.212` layouts need explicit coverage. A same-revision rehearsal alone does not establish update correctness. Catalog submission can follow installation readiness; it does not remove the host compatibility requirement.

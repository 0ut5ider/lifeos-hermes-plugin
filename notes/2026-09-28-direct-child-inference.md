# Direct LifeOS child inference on the isolated gateway

On 2026-09-28, the `.212` gateway accepted Anthropic Messages requests authenticated with `Authorization: Bearer`. The same gateway rejected a request with only `x-api-key` as HTTP 401. A synthetic `READY` request returned a message with `thinking` and `text` blocks. Requests with `output_config.effort` values `low`, `medium`, and `xhigh` each returned HTTP 200. A synthetic one-pixel PNG image block also returned HTTP 200.

The plugin now has an optional direct adapter in `lifeos_hook_bridge/bin/claude_direct.py`. The existing `bin/claude` launcher restores the private gateway settings and selects the adapter when `LIFEOS_CHILD_INFERENCE_DIRECT=1`. The adapter accepts the flags used by LifeOS `Inference.ts`, reads stdin, converts its leading `@image` references to Anthropic image blocks, and returns the Claude CLI JSON fields that `Inference.ts` consumes. It uses Python's standard library. A local HTTP test supplied a fake Claude executable that exited 99; the direct request still succeeded. A second request covered `--system-prompt-file`.

The candidate adapter on `.212` returned `READY` through native `Inference.ts` at low, medium, high, and max levels. The native image-file inference call returned `READY` and reported `flashnext-w4a16-fp8ple` as its executed model. After installation and private opt-in, native medium inference through the installed launcher returned `READY`, and the LAN dashboard returned HTTP 200. All 99 plugin tests passed on `.212` with the native hook paths configured.

This removes the Claude Code CLI from ordinary LifeOS child inference on `.212`. The CLI remains installed as a reference harness. LifeOS `CarrierProbe.ts` intentionally tests Claude Code's own subagent dispatch and is outside the direct inference adapter. The gateway advertises one model, so the four LifeOS model tiers are still mapped to three effort values on that model. LifeOS reports a name-based downgrade for each level; that report has not been changed.

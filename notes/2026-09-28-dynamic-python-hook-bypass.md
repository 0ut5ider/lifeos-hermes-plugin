# Dynamic Python crosses the LifeOS hook boundary

On 2026-09-28, the isolated `.212` Hermes checkout ran a disposable PreToolUse Bash hook. The hook denied a command only when its `tool_input.command` contained the exact text `printf PARITY_PROBE`. The bridge blocked `execute_code` source containing `os.system("printf PARITY_PROBE")`. It allowed source containing `os.system("printf " + "PARITY_PROBE")`; the subsequent Python process returned exit code zero and printed `PARITY_PROBE`.

The bridge sees the outer Python source before Hermes sends it to the persistent kernel. The kernel executes the source with `exec(compile(...))`. No hook runs when that source later assembles a shell command or opens a file through Python. Hermes's separate `check_execute_code_guard` can approve the whole source; it does not run LifeOS's command-specific hooks on effects made inside the cell.

The test used a temporary hook and a harmless marker command. A separate direct call to the real local Hermes `execute_code` function ran the dynamic source in its persistent kernel. Its JSON result had `status: success`, `tool_calls_made: 0`, and output `BEFORE`, `AFTER`, and `PARITY_PROBE`. The remote kernel was not tested.

This initially looked like a Hermes hook parity gap. The [Claude Code hook contract](https://code.claude.com/docs/en/hooks) shows that a Bash PreToolUse hook receives the tool's `command` text. It does not receive effects performed later by the command. A Claude Bash call containing `python -c 'import os; os.system("printf " + "PARITY_PROBE")'` has the same visibility limit. The result establishes a common limit of source-text guards, not a difference from Claude Code. Stronger enforcement would require a restricted kernel or mediated effects, which is a separate feature and would need end-to-end tests.

A disposable Bubblewrap check on `.212` confirmed that a Python 3.14.7 process can start with most of the home directory absent: it ran a subprocess but could not read `~/.hermes/config.yaml` because the path was not mounted. That establishes filesystem isolation as available on this Linux host, not a complete mediation design. In particular, subprocess execution was still possible. Python's [audit hook documentation](https://docs.python.org/3.14/library/sys.html#sys.addaudithook) also says language-level audit hooks are unsuitable as a security sandbox.
